# Codebase review

Scope: full repository as of `3b4b63b` (branch `agent/history-review`). Reviewed the application (`src/App.svelte`, `src/main.js`), build/deploy config (`vite.config.js`, `scripts/verify-base-paths.mjs`, `.github/workflows/verify-and-deploy.yml`), the Playwright E2E suite (`tests/e2e/**`), and the product docs (`VISION.md`, `MVP_DESIGN.md`, `MVP_UX_DESIGN.md`, `README.md`). `npm run check` (svelte-check) and `npm run build` both pass cleanly; `npm audit` reports zero vulnerabilities.

This is a **clinical dosage-calculation prototype**: a phone-first Svelte SPA that converts a vial concentration and an ordered dose into a volume to administer. Correctness, unit-safety, and "never show an answer that wasn't reviewed" are the actual product, so this review weighs those more heavily than a typical CRUD app.

## Summary

The engineering discipline here is unusually high for a ~850-line single-file prototype: the safety model (hide the answer until every equation is individually checked, reset review state on any input change, block incompatible units) is implemented consistently and is backed by E2E tests that assert the *absence* of shortcuts, not just the happy path. The main risks are architectural, not logical: all state, math, and ~250 lines of CSS live in one `App.svelte`, the safety-critical arithmetic has no unit tests independent of the DOM, and two things the docs promise (a CSP, a subsetted math font) aren't in the shipped build yet.

## Good patterns worth keeping

- **Single choke point for "critical change" resets.** Every input that affects the calculation (`medicationAmount`, `vialUnit`, `vialVolume`, `finalVolume`, `orderedDose`, `orderedUnit`) routes through `criticalChange()` (`src/App.svelte:164`), which clears `reviewed`, `checkedSteps`, and `acknowledged`. This is the crux of the product's safety model — a stale review can never be reused — and it's centralized instead of duplicated at each call site.
- **The review gate can't be defeated by re-derived state.** `allStepsChecked` requires every step id present in `calculationSteps` to also be in `checkedSteps` (`src/App.svelte:88`); `completeCalculationReview()` no-ops unless that's true. Combined with the dialog opening with `checkedSteps = []` every time (`openCalculationDetails`, `src/App.svelte:292`), a previously-reviewed calculation can't silently stay "reviewed" after being reopened.
- **Unit-dimension safety is enforced structurally, not just validated.** `unitDimension()` puts `units` in its own dimension so mass↔activity conversion is impossible by construction, and the ordered-unit `<select>` only ever offers options compatible with the vial unit (`src/App.svelte:412-420`) rather than relying on a validation message after the fact.
- **The one-vial dose ceiling makes a second, separately-required check redundant by construction.** `error` blocks when `dose > availableInOrderedUnit` (`src/App.svelte:54`). Algebraically this already guarantees `administrationVolume ≤ finalVolume` (since `administrationVolume = dose·finalVolume/availableInOrderedUnit`), which is the other blocking rule `MVP_DESIGN.md` lists separately. Worth a one-line comment noting the two checks are the same constraint, so a future edit doesn't "fix" a phantom gap by adding a redundant check that can disagree under floating-point rounding.
- **E2E tests assert what must *not* be present, not just what's expected.** E.g. `002-containers-and-validation` asserts no `.result-number` exists before review is complete; `004-privacy-and-recovery` instruments `fetch`/`XHR`/`sendBeacon` and asserts zero calls, then asserts `Object.keys(localStorage)` is exactly the two expected keys — a regression that added a stray storage key or a network call would fail CI, not just an unreviewed diff.
- **Recovery-from-corruption is tested, not assumed.** `004-privacy-and-recovery` deliberately corrupts `dosage.favourites.v2` JSON and asserts the calculator still works while persistence disables itself with a visible message — matches the `onMount` try/catch in `src/App.svelte:101-110`.
- **CI runner choice is deliberate, not incidental.** The Playwright job pins `macos-14` specifically (`.github/workflows/verify-and-deploy.yml:26`) to get deterministic font rendering for the zero-pixel-diff screenshot tests, and `playwright.config.ts` disables GPU/subpixel rendering and reduced-motion for the same reason. This is the right trade for a suite that asserts `maxDiffPixels: 0`.
- **Deployment path correctness is a real, automated check**, not a hope: `scripts/verify-base-paths.mjs` greps the built `dist/` for any absolute `/...` reference that doesn't start with the PR's base path and fails the build — this exists because the app is deployed to per-PR subpaths (`/dosage/pr123/`), a class of bug (absolute-root asset URLs breaking under a subpath) that's easy to introduce and easy to miss visually.
- **Docs and code are honest about the prototype/MVP boundary.** `README.md` explicitly says features described in `MVP_DESIGN.md` (service worker, IndexedDB, CSP) are not yet shipped, rather than letting the aspirational docs imply the running app already meets them.
- **Generated walkthrough docs stay in sync with tests.** `TestStepHelper.generateDocs()` writes each scenario's `README.md` from the same assertions that ran, so the docs can't drift from what's actually verified (only regenerated deliberately via `UPDATE_E2E_DOCS=1`).

## Issues and remediation items

### Correctness / safety-critical logic

1. **No unit tests for the calculation math, independent of the DOM.** `unitFactor`, `unitDimension`, and the concentration/administration formulas (`src/App.svelte:33-63, 154-162`) are only exercised indirectly through Playwright, which drives a real browser through the UI. For a dosage calculator, the arithmetic core is the highest-value thing to have fast, exhaustive, non-UI tests for — property tests like the ones `MVP_DESIGN.md:225` already specifies (`Va × Cpd = D`, doubling `D` doubles `Va`, mg/mcg equivalence, `Vv`-independence) aren't implemented anywhere. **Remediation:** extract the pure functions into a module (e.g. `src/lib/calculation.js`) and add a Vitest (or similar) suite covering the corpus in `MVP_DESIGN.md:211-225` plus edge cases (very small/large numbers, values that round to zero at 6 significant digits, `NaN`/`Infinity` guards). This also unblocks the "isolated, unit-tested pure module" requirement `MVP_DESIGN.md:53` already states as a release gate.
2. **Stale `orderedUnit` state when `vialUnit` changes dimension.** `selectVialUnit()` (`src/App.svelte:171`) updates `vialUnit` and calls `criticalChange()`, but never re-validates or resets `orderedUnit`. If a user has `orderedUnit = 'mcg'` selected and switches the vial to `units`, the `<select>` re-renders with only a `units` option and shows blank (confirmed by the app's own test at `tests/e2e/002-containers-and-validation/002-containers-and-validation.spec.ts:115`), but the underlying `orderedUnit` variable is still the stale `'mcg'` string until the user explicitly picks something. This is currently harmless only because `compatibleDimensions` (`src/App.svelte:39`) independently catches the mismatch and blocks the result — but it's relying on a second mechanism to save a first one that's silently wrong. **Remediation:** have `selectVialUnit` reset `orderedUnit` to `''` (or the dimension-appropriate default) whenever the new vial unit's dimension differs from the current ordered unit's, so the visible state and the bound state can't diverge.
3. **Saving the same reviewed mix twice creates duplicate history entries.** `saveMix()` (`src/App.svelte:235`) never resets `reviewed`/`acknowledged` after a successful save, so the "Save mix on this phone" button stays enabled and a second click (e.g. a double-tap on a touch screen) pushes a second, functionally identical record with a new timestamp. Low risk (it's history, not the calculation itself) but worth a debounce or a post-save state reset for data hygiene, since the history list is explicitly documented as "an audit aid" (`VISION.md:67`).
4. **Individual delete has no confirmation while "clear all" does.** `deleteFavourite`/`deleteHistory` (`src/App.svelte:227, 276`) delete immediately on click; `clearHistory` (`src/App.svelte:284`) requires `window.confirm`. That inconsistency is minor since these are non-patient records, but a stray tap on "Delete" in a crowded list has no undo — consider at least a brief "Removed — Undo" toast, consistent with the app's general care about accidental data loss elsewhere.

### Architecture / maintainability

5. **Everything lives in one 855-line `App.svelte`.** State declarations, ~15 reactive (`$:`) statements, all business logic, all three screens' markup, and ~250 lines of CSS (with a second, overlapping "fixed-height redesign" pass appended after the first responsive pass — see `src/App.svelte:607-718` vs. `725-855`) are in a single file. It's currently navigable because the app is small, but there's no structural boundary yet between "safety-critical calculation" and "UI," which makes the calculation harder to unit-test (see #1) and makes future features (more unit types, multi-vial math) riskier to add without touching rendering code. **Remediation:** before the next feature, split into at minimum a calculation module, a storage module (the `read`/`write`/`storageKeys` local-storage layer, `src/App.svelte:9-12, 112-127`), and per-screen components (`Mix`, `Favourites`, `History`).
6. **CSS has two layered passes rather than one coherent set of rules.** The block at `src/App.svelte:607-724` implements a normal scrolling responsive layout; the block at `725-855` immediately overrides large parts of it (`html`/`body` become `overflow: hidden`, `.app-shell` becomes a fixed grid, most component paddings/sizes are redeclared) to retrofit the "no-scroll instrument panel" redesign (`164c0b9`, "Redesign calculator without scrolling"). It works — svelte-check and the layout-overflow E2E assertions all pass — but a reader has to mentally apply patch 2 on top of patch 1 to know the real size of anything. **Remediation:** the next time this file is touched, fold the override block into the original rules instead of layering a second block after it.
7. **History pagination is implemented as "render one item, filtered from a full loop" instead of slicing.** `{#each history as item, index}{#if index === historyPage}` (`src/App.svelte:552-553`) iterates and discards the entire array to show a single record, in contrast to the cleaner `visibleFavourites = favourites.slice(...)` approach used one screen over (`src/App.svelte:96-99`) which shows 6-per-page. The two nearly-identical list screens (Favourites, History) end up with different pagination UX (6-per-page grid vs. one-record-at-a-time) for no stated product reason. **Remediation:** align on one pagination behavior (probably the favourites one, since 6-at-a-time is more usable) and reuse a `slice`-based approach for both.

### Performance / bundle size

8. **KaTeX ships its entire font family (~1.1 MB across 59 font files) for a UI that only ever renders digits, a comma, a decimal point, `×`, `\frac`, and a handful of unit abbreviations (`mg`, `mcg`, `mL`, `units`).** A production build (`npm run build`) produces a 2.0 MB `dist/`, of which ~1.1 MB is `KaTeX_*` woff/woff2/ttf files for font families (Fraktur, Script, Caligraphic, Size1-4, SansSerif, Typewriter, …) the app's expressions never use, because `import 'katex/dist/katex.min.css'` (`src/App.svelte:4`) pulls in every `@font-face` KaTeX ships. The JS bundle itself is 321 KB (100 KB gzip), most of which is the KaTeX renderer. For a PWA aimed at "bright, dim, noisy, interrupted, gloved, low-connectivity" clinical settings (`VISION.md:11`), first-load size matters more than usual. **Remediation:** either self-host a subsetted KaTeX CSS covering only the glyphs actually used (KaTeX supports font subsetting), or, given the visual vocabulary is genuinely narrow (fractions, roman-text units, digits), consider hand-rolling the four equation shapes with plain HTML/CSS and MathML `annotation` for accessibility instead of a full TeX renderer. Either would cut the shipped payload by roughly half.

### Security / privacy

9. **No Content Security Policy is shipped**, despite `MVP_DESIGN.md:131` explicitly requiring `default-src 'self'` with no `connect-src` as a release gate, and the README's privacy promise (`README.md:74`) leaning on "restrictive CSP" as one of the enforced controls. `index.html` has no `<meta http-equiv="Content-Security-Policy">` and the GitHub Pages deploy sets no CSP header either. Unlike the service-worker gap (which the README explicitly discloses as not-yet-shipped), the CSP gap isn't called out anywhere the way it's called out as a requirement — it's implicitly assumed. **Remediation:** this is cheap relative to its value: add a restrictive `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; ...">` now (a meta CSP works fine for a static SPA with no inline scripts) rather than waiting for the full MVP push; it directly backs an explicit privacy claim the README already makes to users.
10. **`static/images/dilution-containers.png` (364 KB) is shipped to production unused.** It lives under `static/` (Vite's `publicDir`, copied verbatim into every build) but nothing in `src/App.svelte` references it — only `MVP_UX_DESIGN.md` mentions it, presumably as a design reference image. It currently adds ~18% to the total `dist/` size for zero runtime benefit. **Remediation:** move it out of `static/` into `design/mockups/` (which already holds the other non-shipped reference images and isn't part of the Vite public dir) or delete it if superseded.

### Testing

11. **The Playwright suite is the only safety net for the calculation logic**, and it's inherently slower and more environment-sensitive (font rendering, OS, browser flags) than a pure-function suite would be — see #1. This isn't a flaw in what exists (the E2E coverage is genuinely thorough: accessibility via axe, network isolation, corruption recovery, viewport overflow, pagination boundaries), just a gap in what's *missing* underneath it.
12. **`@axe-core/playwright` is used in exactly one spec** (`005-responsive-accessible`), only in the "review calculation" dialog state on one project run per journey. That's reasonable as the canonical accessibility check, but the other four journeys (favourites list, history list, error states, empty states) never get an automated axe pass — those are visually and structurally distinct enough (different ARIA roles, dynamic list content, `role="alert"`) that a regression specific to one of them wouldn't be caught. **Remediation:** low cost to add a lightweight axe check to the favourites/history "empty" and "populated" steps, or add an explicit `# 010 - Recovery and migration` axe check as the docs already scope in `MVP_DESIGN.md:209`.
13. **`MVP_DESIGN.md:196-209` documents ten planned scenarios (001–010) but only five exist** (`001-cross-unit-calculation` … `005-responsive-accessible`, roughly covering the documented 001/004/009 plus parts of others). Missing relative to the doc: an explicit offline/service-worker journey (008 — blocked on the service worker itself not existing yet, so this is expected), and an explicit schema-migration/quarantine journey (010) beyond the corruption case already covered in 004. Not urgent, but worth tracking so the numbered gap doesn't quietly become permanent as the "current state" list in the README is updated.

### Documentation

14. **The design docs (`VISION.md`, `MVP_DESIGN.md`, `MVP_UX_DESIGN.md`) are unusually rigorous** — genuinely worth calling out as a strength, not just a gap-list target. The numeric policy, blocking-validation list, data model, and safety principles are all specific enough to write tests against, and mostly *have* been (the deterministic calculation corpus in `MVP_DESIGN.md:211-224` maps almost 1:1 onto `tests/e2e/002-containers-and-validation`). The main documentation risk is drift as the prototype grows past what the current single-file architecture can comfortably hold — worth revisiting the docs alongside the architecture split in #5.
15. **Regulatory/clinical-use framing is consistently applied** across `README.md`, `VISION.md`, and the in-app banner (`src/App.svelte:327-330`), which is exactly the kind of thing that's easy to state once and then let drift out of sync with the actual UI. Currently it isn't drifted — worth keeping an explicit check (e.g., a Playwright assertion that the prototype banner text is present, similar to what already exists for other safety copy) so a future redesign can't accidentally drop it.

## Suggested priority order

If picking a small number of things to act on next, in order of value-to-effort:

1. Add the CSP meta tag (#9) — minutes of work, closes a stated privacy gap.
2. Move/delete the unused 364 KB image (#10) — trivial, immediate size win.
3. Extract the calculation core and add a pure unit-test suite against the documented corpus (#1) — the single highest-leverage change for a dosage calculator's actual risk profile.
4. Fix the stale `orderedUnit` state on vial-dimension change (#2) — small, removes a latent inconsistency that currently only survives because of a second guard.
5. Subset or replace the KaTeX font loading (#8) — larger effort, meaningful payload win for the target low-connectivity clinical setting.
